# ML-12736 — Pydantic 2 / FastAPI upgrade POC

**Ticket:** ML-12736 "KFP 2 in mlrun service"
**Branch:** `worktree-pydantic-v2-poc` (worktree off `development` @ 0cac732d7)
**Venv:** dedicated `.venv` in the worktree (mutable deps; main repo `.venv` untouched)

---

## 1. Objective

Upgrade the **API server** to Pydantic 2 + latest FastAPI (prerequisite for KFP 2),
while the **client** (mlrun-kfp image / SDK) stays on KFP 1.8 + Pydantic 1.

Dependency chain (from the ticket):
- New FastAPI requires native Pydantic 2 models.
- KFP 1.8 pins `pydantic<2`.
- Pydantic 2 is not backward-compatible with v1.

So the shared schemas in `mlrun/common/schemas/` must be made FastAPI-acceptable on the
server (native v2) without breaking the v1 client.

## 2. Environment (what the POC venv resolved to)

| Package | Before (development) | POC (server flavor) |
|---|---|---|
| pydantic | `>=1,<2` → 1.10.x | **2.13.4** (`>=2,<3`) |
| fastapi | `~=0.125.0` | **0.136.3** (`>=0.128.0`) |
| starlette | — | 1.3.1 |
| kfp_server_api | 1.8.5 | 1.8.5 (unchanged for now) |
| kfp | not in api flavor | not installed |

Only two lines changed in `dockerfiles/mlrun-api/requirements.txt`:
```
fastapi>=0.128.0          # was fastapi~=0.125.0
pydantic>=2,<3            # was pydantic>=1,<2
```
**Key topology finding:** base `requirements.txt` does NOT force `pydantic<2`. The
`mlrun-pipelines-kfp-v1-8` adapter listed there (without the `[kfp]` extra) only pulls
`inflection` + `kfp_server_api~=1.8` — no `kfp`, no pydantic pin. Real `kfp~=1.8.23`
(which pins `pydantic<2`) only arrives via the `kfp18` extra. So the *only* thing pinning
the server to pydantic 1 was the explicit line in the api requirements. `mlrun` imports
cleanly under pydantic 2 because every schema already uses the `pydantic.v1` namespace.

## 3. Reproduction of the failure

`pydantic.v1` schema is a latent instance of this error.

## 5. Strategy options

### Option A — Server-side v2 schema package (literal ticket / "migrate to server/py")
Create native-v2 copies of the server-touched schemas in `server/py` and repoint server
code (`mlrun.common.schemas.X` → server pkg). `mlrun/common/schemas` stays v1 for the
client AND for the mlrun SDK code the server imports.
- ✅ Strongest isolation; SDK code behaviorally unchanged server-side; matches ticket wording.
- ❌ Largest/riskiest mechanical change (~2,544 refs / 134 files / 172 endpoints); two
  schema definitions to keep wire-compatible; needs ruff `known-local-folder` +
  import-linter root-package additions.

### Option B — Conditional `_v1`/`_v2` subpackages inside `mlrun.common.schemas`  *(recommended)*
`mlrun/common/schemas/__init__.py` dispatches by installed pydantic version:
```python
import pydantic
if int(pydantic.VERSION.split(".")[0]) >= 2:
    from ._v2 import *   # native pydantic 2 (server image)
else:
    from ._v1 import *   # pydantic.v1 (client / mlrun-kfp image)
```
~38 new native-v2 files + dispatcher; **near-zero** call-site churn; same import path
everywhere. Physically separates the two schema sets (satisfies the ticket's intent),
and is trivially reversible (drop `_v1`, collapse `_v2`) once the client moves to v2.
- ✅ Tiny mechanical footprint; no endpoint signature edits; reversible.
- ❌ Schemas stay in `mlrun/common` (not `server/py`); under the server's pydantic-2 env,
  ALL mlrun code (server + SDK) uses v2 schemas → broader behavioral surface to validate;
  must keep `_v1`/`_v2` wire-compatible.

### Option C — In-place `pydantic.v1` → native `pydantic` (single source)
Flip every schema to native `pydantic`; v1 on client, v2 on server; fix the 9 `const=`.
- ✅ Least code of all.
- ❌ No physical separation (contradicts the ticket); permanent dual-version-compat tax on
  one source; same broad behavioral surface as B.

---

## 6. Decision

> **DECIDED: Option A** — native-v2 schema package in `server/py/schemas/`, repoint server
> code (`mlrun.common.schemas.X` → `schemas.X`). `mlrun/common/schemas` stays `pydantic.v1`
> for the client and the mlrun SDK. Chosen for strongest client/server isolation, matching
> the ticket's explicit "separate the schema of the client and server" requirement.

### (For the record) Recommendation analysis

For both the POC and likely production: **Option B**. It satisfies the ticket's actual
goal (separate client/server schema definitions, reversible later) at a fraction of the
effort and risk of Option A, and avoids touching 2,544 call sites + 172 endpoint
signatures. Option A is the most conservative for SDK behavior but is a large, error-prone
mechanical migration; worth it only if the team specifically wants SDK code to keep
operating on v1 schema objects even inside the pydantic-2 server.

All options must guarantee **wire compatibility**: a v1 client and a v2 server exchange
JSON, so the v2 schemas must serialize/parse to byte-identical JSON shapes.

**Achieved (Option A):** every `mlrun.common.schemas` module mirrored to native pydantic-2
`server/py/schemas/`, server code repointed, and the full API app constructs cleanly.

| Proof | Result |
|---|---|
| `services.api.daemon.app()` builds | **342 routes registered** (242 unique paths) |
| `app.openapi()` (builds JSON schema for every model) | **OK** — 121 paths, 178 component schemas |
| v1↔v2 field-equivalence over all modules | **ALL GOOD** (`.poc_verify_all.py`) |
| FastAPI acceptance of every top-level model | **129/129 accepted, 0 rejected** |
| `PydanticV1NotSupportedError` | **gone** |

### What was built
- `server/py/schemas/` — native pydantic-2 mirror of all 38 schema modules
  (29 converted by a fan-out workflow, 6 no-pydantic copied verbatim, 2 re-export hubs,
  + the base `object.py`).
- Server code repointed: **133 files / ~2,700 refs** `mlrun.common.schemas` → `schemas`
  (tests excluded — see follow-ups).
- `dockerfiles/mlrun-api/requirements.txt`: `pydantic>=2,<3`, `fastapi>=0.128.0`.

### v1→v2 conversion rules applied (all validated empirically)
1. `from pydantic.v1` / `import pydantic.v1` → native `pydantic`.
2. **Implicit-optional → explicit `= None`** (v1 auto-defaults Optional; v2 makes it required) —
   ~167 fields; a bare `Any` field is also implicitly-optional in v1 (caught `ScheduleInput`).
3. `class Config` → `model_config = ConfigDict(...)`; `orm_mode`→`from_attributes`,
   `allow_population_by_field_name`→`populate_by_name`, `Extra.allow`→`extra="allow"`.
4. `Field(..., const=True)` → `Literal[...]` (v2 hard-removed `const`).
5. `conlist(min_items/max_items)` → `min_length/max_length`; `regex=`→`pattern=`.
6. **Look-around regex** (e.g. `model_endpoints` `constr(pattern=...)`, `tags.py` Path) — pydantic
   v2's default Rust engine rejects look-around. Fixed via `ConfigDict(regex_engine="python-re")`
   on the models, and a Python-`re` `AfterValidator` for the FastAPI path constraint.

### Runtime bugs the smoke test drove out (all server-side, now fixed)
1. **`NameError: 'mlrun' is not defined`** — the blanket import repoint replaced
   `import mlrun.common.schemas` (the sole `mlrun` binding in 4 files) → restored with
   `import mlrun` / `import mlrun.errors`.
2. **Implicit-`Optional`** — pydantic v1 auto-defaults a `= None` field to Optional; v2 rejects
   explicit `None` on a non-Optional type. 14 fields → `X | None`. (Also a bare `Any` field.)
3. **`ClientSpec` v1 str-coercion** — bool/int configs feed `str` fields; v1 coerced
   (`True`→"True"), v2 is strict → `mode="before"` validator reproduces it.
4. **Content-Type middleware (the critical shim)** — FastAPI 0.136 only JSON-parses a body when
   `Content-Type: application/json` is set; mlrun v1 clients send bodies via `requests data=`
   without it, so **every write endpoint** 422'd (`create_project`, `store_secret_tokens`, …).
   `EnsureJSONContentTypeMiddleware` defaults missing Content-Type to `application/json` for
   body-bearing requests (explicit yaml/zip/form preserved). This is the single most important
   server change for v1-client compatibility under the new FastAPI.
